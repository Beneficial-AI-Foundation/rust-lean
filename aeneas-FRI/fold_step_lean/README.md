# FRI Fold-Step Verification (Rust &rarr; Aeneas &rarr; ArkLib)

Formal verification of the **arity-2 FRI folding step** &mdash; the core
arithmetic operation inside every round of the
[FRI](https://eccc.weizmann.ac.il/report/2017/134/) protocol.

This project demonstrates a **minimal but meaningful** pipeline:

```
Rust source  ──Charon──▸  LLBC  ──Aeneas──▸  Lean 4  ──proofs──▸  ArkLib specs
fold_step/src/lib.rs    .llbc           FoldStep/Funs.lean     FoldingCorrectness.lean
```

Unlike the companion project
[`fold_arity_lean/`](../fold_arity_lean/) (which verifies the scheduling
function `compute_log_arity_for_round` &mdash; pure integer arithmetic), this
project verifies a function that performs **actual field-arithmetic folding**,
where [ArkLib](https://github.com/Verified-zkEVM/ArkLib)'s polynomial
specifications (`foldNth`, `splitNth`, `Domain`) are genuinely needed.

## What is fold_step?

Given evaluations `lo = f(x)` and `hi = f(&minus;x)` of a polynomial over a
prime field **F_p**, a verifier challenge **&beta;**, and precomputed inverses
**x&supmin;&sup1;** and **2&supmin;&sup1;**, the function computes:

```
fold_step(lo, hi, β, x⁻¹, 2⁻¹, p)  =  ((lo + hi) + β · (lo − hi) · x⁻¹) · 2⁻¹   mod p
```

Mathematically, this equals **`(foldNth 2 f β).eval(x²)`** &mdash; one
evaluation of the degree-halved polynomial produced by a single FRI round.
This is the same operation as Plonky3's `fold_matrix` (arity-2 case in
`two_adic_pcs.rs`) and the `fold_x_row` function in Circle FRI, written as a
standalone pure Rust function suitable for Aeneas extraction.

### Rust source (`fold_step/src/lib.rs`)

```rust
pub fn fold_step(
    lo: u64, hi: u64, beta: u64,
    x_inv: u64, two_inv: u64, p: u64,
) -> u64 {
    let sum  = (lo + hi) % p;
    let diff = (lo + p - hi) % p;
    let t    = (diff * x_inv) % p;
    let bt   = (beta * t) % p;
    ((sum + bt) % p * two_inv) % p
}
```

### Aeneas extraction (`FoldStep/Funs.lean`)

Aeneas extracts this to a monadic `Result U64` function with 13 checked
arithmetic steps (each `+`, `−`, `*`, `%` can fail on overflow or
division-by-zero):

```lean
def fold_step
  (lo hi beta x_inv two_inv p : Std.U64) : Result Std.U64 := do
  let i ← lo + hi;      let sum ← i % p
  let i1 ← lo + p;      let i2 ← i1 - hi;     let diff ← i2 % p
  let i3 ← diff * x_inv; let t ← i3 % p
  let i4 ← beta * t;     let bt ← i4 % p
  let i5 ← sum + bt;     let i6 ← i5 % p
  let i7 ← i6 * two_inv; i7 % p
```

## Theorem inventory

### BasicProofs.lean &mdash; fully proved (0 sorry)

Imports Aeneas, verifies the extracted Rust function directly.

| Theorem | Status | Property |
|---------|--------|----------|
| `fold_step_nat_bounded` | Proved | Pure Nat spec always returns &lt; p |
| `fold_step_spec` | **Proved** | **Key theorem:** Aeneas-extracted function matches `fold_step_nat` and result &lt; p |
| `fold_step_succeeds` | Proved | Function never panics under `SafeFieldParams` |
| 4 concrete examples | Proved | `fold_step_nat` and Rust function agree on p=7 and p=17 |

**`fold_step_spec`** is the central result. It uses Aeneas's `progress` tactic
to step through all 13 checked operations, proving:
- Each intermediate addition/multiplication cannot overflow u64
- Each modular reduction has a nonzero divisor
- The final result equals `fold_step_nat` applied to the input values
- The result is strictly less than `p`

The overflow-freedom proof requires two preconditions bundled in
`SafeFieldParams`: **p&sup2; &le; u64::MAX** (for multiplications) and
**2p &le; u64::MAX + 1** (for additions). Both hold for any prime
p &le; 2&sup3;&sup2; &minus; 1, covering all primes used in practice.

## Mathematical background

FRI (Fast Reed-Solomon IOP) works by repeatedly folding a polynomial:

1. **Split:** decompose `f(x) = f_even(x²) + x · f_odd(x²)`
2. **Fold:** combine with challenge `β`: `g(y) = f_even(y) + β · f_odd(y)`
3. **Result:** `deg(g) ≤ deg(f)/2`, evaluation domain halves

At the evaluation level, given `lo = f(x)` and `hi = f(−x)`:
- `f_even(x²) = (lo + hi) / 2`
- `f_odd(x²) = (lo − hi) / (2x)`
- `g(x²) = f_even(x²) + β · f_odd(x²) = (lo + hi + β·(lo−hi)·x⁻¹) · 2⁻¹`

This is exactly what `fold_step` computes. In ArkLib's notation:
**`g = foldNth 2 f β`** and **`fold_step(lo, hi, β, x⁻¹, 2⁻¹) = g.eval(x²)`**.

## Why ArkLib matters here (vs. fold_arity)

The companion project `fold_arity_lean/` verifies `compute_log_arity_for_round`
&mdash; a pure integer scheduling function. There, ArkLib's polynomial specs
(`foldNth`, `splitNth`, `Domain`) have no direct connection to the function
being verified.

`fold_step` is different: it performs the actual field-arithmetic folding that
ArkLib's `foldNth` mathematically defines. The verification goal is to prove
that **the Rust implementation computes exactly one evaluation of `foldNth 2 f β`**.
This is the first function in the pipeline where ArkLib specifications are
genuinely load-bearing.

| ArkLib concept | What it says | How it applies to fold_step |
|---|---|---|
| `foldNth 2 f β` | mathematical FRI fold | `fold_step` computes one evaluation of this |
| `splitNth 2 f i` | even/odd decomposition | `lo+hi = 2·f_even(x²)`, `lo−hi = 2x·f_odd(x²)` |
| `foldNth_degree_le` | degree halves after fold | soundness: folded poly stays in degree bound |
| `evalDomain D (i+1)` | folded domain | x² lives in the next domain in the tower |
